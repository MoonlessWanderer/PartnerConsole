# PartnerConsole — UX and production preservation contract

This is a proposed durable repository-root UX contract for the approved redesign. It is not a replacement for the verified existing API, business policy, or backend validations. Read actual current code/tests and reconcile any mismatch before implementation. All data in reference PNGs is illustrative only.

## Role, security and request behavior

- Keep the admin and partner login paths, `lib/adminEntry.ts`, route role guard, actual backend authentication, session binding and account display. No discovery link to admin login from partner/public screen, no hardcoded credentials, no bypass/debug login route, no auth weakening. Preserve existing `pp_token`, `pp_role`, `pp_username` behavior unless an independently approved security migration is planned; do not copy tokens into query strings, logs, screenshots, fixtures checked into repo or rendered HTML. Preserve `logoutSession` server revocation semantics: only clear/redirect after successful/401/403 revocation response; on network failure retain session, show actionable error and re-enable logout. Prevent double requests. Preserve session-change listeners, 401 handling and role checks. Do not change CORS or security headers.
- Maintain `lib/api.ts` response validation, safe sanitized error messages, 45-second request deadline (including body), `reviewSession` check, distinction of read vs unknown write result, public error code handling. Never display raw stack traces/backend exceptions, V2Board secrets, credentials or internal URLs to unauthorized viewers. Unknown mutation outcome is not success or guaranteed failure: warn to check state before retry, no auto-resubmit. All status and success claims from verified responses. Mask sensitive subscription links, tokens, credentials and panel secure paths in test artifacts.
- Keep existing input constraints, endpoint paths and request/response DTOs. Use React state and existing logic, not client-side invented calculations. No direct network calls to production panel, no live credential collection. Local fixture-only screenshot/test data; real API in production.

## Financial consent and high-risk mutations (non-negotiable)

- Create/increase/decrease/delete/reset-traffic must use actual current code's quote/consent semantics. Read `app/partner/subscriptions/new/page.tsx`, `app/partner/subscriptions/[id]/page.tsx`, `lib/types.ts`, `components/QuoteBox.tsx`, `components/PurchaseWalletBreakdown.tsx`, `lib/api.ts`, backend consent/billing/subscriptions. Don't change semantics by replacing these controllers with visual-only form code.
- Preserve exact quote identity (account/session, action, product, subscription, draft, rate/credit context), `reviewSession`, `quoteVersion` invalidation, stale/out-of-order quote handling, `consent_token` from server, `affordable`, shortage, locks and explicit final action. Do not cache consent in URL/localStorage or reuse across account, changed product/user/volume/end date/note/state or expired quote. On financial_consent response invalidate old review, fetch fresh quote, display real changed values, and require explicit reconfirmation, not auto-submit. If account switches in another tab old draft/quote cannot commit under new account. Preserve duplicate-submit prevention using synchronous ref/appropriate locks and disabled/busy UI; state-only lock is insufficient for race. A user click on mobile “مشاهده پیش‌فاکتور” only reviews, never charges. Desktop primary button commits only after a valid reviewed quote. Do not claim confirmation until real response; display operation reference/recovery if API reports one.
- Show exact actual wallet deduction in تومان and distinct volume/day product credits. For create: need GB/days, consumed credit quantities, paid remaining GB/days, rates × paid quantities, costs by unit, final wallet deduction, insufficient balance/shortage, selected product/normalized username/expiry. Keep full breakdown and current eligibility visible at the point of consent. Never sum GB, days and toman, convert to rial, round away meaningful precision, or substitute reference values. Increase/decrease/delete/reset show the correct server quote consequences, actual charges/refunds and not arbitrary cash equivalents. Preserve server-side policy for decrease/refunds/delete; distinguish returned volume/day credits and wallet charges. For ban/unban/reset-link/note keep actual actions and confirmation where appropriate, no imaginary prices. Disabled when forbidden or busy, with reason; unknown/missing live data never silently replaced with 0.
- Admin partner adjustment uses existing `/admin/partners/{id}/adjust` contract: asset `toman` (global), `gb` or `days` (product-specific), selected product only if necessary, signed quantity (negative deducts). Preserve backend validations, existing duplicate-submit safety, partial response merge (username, banned state, ID must remain), refresh real balance/credits and report result. Separate adjustment form from view. Clear target account, asset, signed impact and actual unit before confirmation; no invented payment gateway or auto-topup. Preserve create partner, ban/unban and consequences as actual server policy. No fake approval state. Ban is not merely a CSS status.

## Unresolved operations

Reference boards 21–24 are a list, inspection, resolution and final confirmation, NOT generic workflow approvals. Read `lib/attention.ts` and `app/admin/operations/page.tsx` for exact controls; do not recreate financial decision logic from the screenshots. Preserve `OperationStatus`: pending (در انتظار بازیابی), attention (نیازمند بررسی), failed (ناموفق و برگشت‌خورده), completed (انجام‌شده), closed (بسته‌شده توسط ادمین). Filter and render actual types/reasons. Present actual ID, username/partner/product/subscription, charge from wallet/credit, refunds, old/new cap, panel_sent/panel_applied, last sanitized error, previous resolution if present, shortfall, update time.

- Read-only panel state: available/unavailable, exists/no user, owned/not owned. Never show data of unowned panel user; do not infer success from matching/reset values. Busy means no resolution. Only `attention` + not busy + permitted server `decision_blocks` can offer decisions. Retry labels/behavior derive from `retry_action` (`resend_reset`, `resend_change`, `collect_shortfall`), or permitted close. Show blocked reasons. Do not add generic force-retry/force-close. Preserve `decisions`, `blockedDecisions`, `effects`, `explain`, `formProblem`, `resolveBody`, `shownError`, `hasShortfall`, `seen_updated_at` and server re-read/409 handling.
- Display exact wallet/credit, ledger and panel effects and relevant warnings; retain full distinction of no double charge/no double refund and shortfall collection. Mandatory decision note 5–500 chars from existing constants; mandatory panel check checkbox; explicit shortfall acceptance if closing with remaining shortfall. Clearing/reselecting decision must clear inappropriate acceptance. Review and final confirmation separate; “بستن پنجره” distinct from “بستن عملیات بدون جابه‌جایی مالی”. Show note and impacts in final confirmation. Never imply no risks. No auto retry. Preserve final payload, including `seen_updated_at`, `accept_shortfall` when applicable; refresh/review on changed state. Use original Persian safety text, even if longer than the PNG.

## Navigation, localization, and state continuity

- Real routes remain reachable; subroutes may be introduced for substantial tasks if all API/permission/refresh/back states work. Preserve user-entered non-sensitive search, URL `q`, `offset`, `limit` and `listQuery` return context; use existing limit 50 for partner list. Do not reset to first page unexpectedly after details. On filter/search changes reset/clamp paging correctly; keep no-results distinct from empty records. Debounce and cancel/ignore stale remote queries, immediate clear, prevent IME submission while composition active. Do not introduce pagination/filter/count for truncated datasets without correct support. Ledger read-only; signed asset amounts correctly formatted. Do not produce data with sample fixture values in real UI.
- Preserve the current local Vazirmatn font and its original font assets, declarations, weights and fallback order; no font substitution or new font dependency. Verify browser font loading on desktop/mobile. Preserve `fa` and `dir="rtl"`, current Jalali date conversion/calendar, local time/date semantics; maintain existing format helpers (including exact Persian numerals and tested financial text). Use logical CSS properties, `<bdi>`/LTR for IDs, usernames, URLs, dates and signed amounts; calendar Persian labels, no silent Gregorian conversion. Input accepts valid forms the server accepts; preserve pattern, min/max, required constraints, optional notes; do not force unrelated input units. Keep consistent action wording across route, button, modal and result.
- Form labels real `<label>`, associated errors and helper text, focus first invalid field; preserve input on recoverable error. Confirm route-leave if unsaved sensitive draft would be lost (never store secrets in persisted drafts). No browser alert/confirm/prompt for product UI. Show app-owned accessible confirmations and in-context feedback. Keyboard focus restores to trigger or appropriate page heading after navigation. Manage drawer focus/keyboard and background inertness; mobile bottom bar safe area with content padding, no fixed footer covering last rows or controls. Use anchor links for navigation, buttons for actions; no div-only interactions. Keyboard, touch, reduced motion, contrast and long-content/zoom work. Do not add phantom buttons to match a picture.

## State matrix and evidence

For every affected route/state, cover: initial loading/session verification, valid normal data, empty/no results, server/network failure with safe recovery, mutation pending, duplicate-click, success, disabled/forbidden, confirmation/cancel, refresh/back/deep link, narrow mobile and keyboard. Where relevant: quote expiry/change/insufficient balance, account switch, unknown mutation outcome, stale operation, panel unavailable/unowned, shortfall and blocked decisions, expired/banned subscriptions, long text, large/negative/decimal quantities, secret masking, 401/logout failure. Use deterministic isolated tests/fixtures. Real financial tests must use the project's existing safe local harness, never real accounts/panels.

Existing test suites include `security-client.test.cjs`, `attention-client.test.cjs`, `financial-consent-browser.cjs`, backend financial/security/recovery/upgrade and installer regressions. Browser selectors may be migrated to meaningful roles/labels/test IDs, but retain all business assertions. Add tests for new responsive interaction/navigation and state behavior. Do not declare success without recording actual check outcomes. Design cannot reduce any financial, permission, packaging or accessibility guarantee.


All owner-facing implementation and verification reports must be in Persian, with technical identifiers/logs retained as needed. The Persian report must explicitly record unchanged font assets, actual font-loading evidence, remaining differences and test outcomes.

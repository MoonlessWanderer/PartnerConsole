# راه‌اندازی و ارتقای Production

این رویه برای یک مقصد MySQL/InnoDB ازپیش‌آماده یا SQLite پایدار است. مسیر Production با مقدار دقیق `ENVIRONMENT=production` فعال می‌شود. تست واقعی MySQL نیازمند محیط آزمایشی مجاز است. [راهنمای نصب دستی](INSTALL.md)

## آماده‌سازی و شروع

1. ابتدا روی محیط آزمایشی مجاز، نسخهٔ برنامه و schema، مقصد اتصال، دسترسی‌های حساب، پشتیبان و بازیابی را بررسی کنید. schema خالی MySQL باید پیش از فرمان و در محیط مورد تأیید آماده باشد. برای ارتقا، پذیرش درخواست‌های نوشتن را ببندید و همهٔ workerها و ابزارهای مهاجرت یا بازیابی را متوقف کنید. وضعیت pending، attention و leaseهای فعال را ثبت کنید.
2. پشتیبان سازگار از داده و revision بگیرید و پیش از ارتقا روی مقصد جدا بازیابی کنید. نسخهٔ قبلی artifact و ارجاع امن کلید رمزنگاری پنل را ثبت کنید. نشانی دیتابیس و secrets را از مسیر امن به فرآیند بدهید و مقصد را قبل از اجرا مستقلاً بررسی کنید.
3. از پوشهٔ `backend` و محیط Python همان نسخه اجرا کنید. `DATABASE_URL` باید صریح و پایدار باشد. برای نصب تازه `ADMIN_USERNAME` و یک `ADMIN_PASSWORD` قوی و غیرپیش‌فرض تنظیم کنید. نام کاربری یا رمز موجود در اجرای مجدد عوض نمی‌شود.

   ```powershell
   $env:ENVIRONMENT = 'production'
   python -m app.bootstrap_database
   if ($LASTEXITCODE -ne 0) { throw 'Bootstrap failed. Keep the API stopped.' }
   ```

4. پس از exit code صفر و بررسی revision و سلامت schema، workerها را تحت مدیر سرویس شروع کنید. نمونهٔ محلی پشت proxy مستقر روی همان میزبان:

   ```powershell
   python -m uvicorn app.main:app --host 127.0.0.1 --port 8741 --workers 2 --lifespan on
   ```

5. صحت هدرها، رد درخواست بدون نشست، ورود ادمین آزمایشی، دفترکل و وضعیت عملیات معوق را بررسی کنید. پس از تطبیق اثرهای پنل و دیتابیس، پذیرش درخواست‌های نوشتن را باز کنید.

فرمان نگهداری ابتدا تنظیمات امنیتی را اعتبارسنجی می‌کند، مهاجرت را روی اتصال نگهداری اجرا می‌کند و پس از موفقیت مهاجرت، تنها در جدول خالی ادمین می‌سازد. در SQLite، `BEGIN IMMEDIATE` اجراهای فرمان را سری می‌کند. در MySQL، قفل نام‌دار به schema و همان نشست مهاجرت وابسته است و اجرای دوم در صورت اشغال قفل متوقف می‌شود. این قفل برای همان سرور MySQL است. ابزار مستقلی که قفل را رعایت نمی‌کند یا workerهای ازقبل فعال با آن متوقف نمی‌شوند. برای نگهداری همهٔ نویسنده‌ها باید متوقف باشند.

worker در Production، پیش از شروع بازیابی، تطابق مجموعهٔ revisionهای دیتابیس با head برنامه و وجود ادمین را بررسی می‌کند. ادمین دارای رمز پیش‌فرض باعث رد راه‌اندازی می‌شود. در MySQL، worker وجود قفل نگهداری فعال را نیز بررسی می‌کند. کنترل revision جای بازرسی schema و تطبیق داده را نمی‌گیرد. بازیابی در worker با همان lease و قواعد pending و attention انجام می‌شود. اجرای Development همچنان مهاجرت و seed خودکار دارد.

## شکست، بررسی و بازیابی

- کد خروج غیرصفر یعنی workerها باید متوقف بمانند. مرحلهٔ خطا، revision، نسخه artifact و زمان اجرا را ثبت کنید. خطاهای اتصال یا SQL ممکن است حاوی جزئیات حساس باشند و باید در محیط محدود و بدون انتشار secrets بررسی شوند. فرمان نگهداری نوع خطا را در خروجی عادی نشان می‌دهد.
- روی نسخهٔ آزمایشی از وضعیت شکست‌خورده، revision را با ساختار واقعی جدول‌ها، ایندکس‌ها و داده‌ها مقایسه کنید. در SQLite، تست محلی rollback مهاجرت را تأیید می‌کند. در MySQL، DDL ممکن است commit ضمنی داشته باشد و بخشی از تغییرات باقی بماند.
- در MySQL فرمان را روی schema نیمه‌تمام کورکورانه تکرار نکنید. `alembic stamp`، حذف جدول، downgrade مخرب یا تغییر دستی revision فقط پس از تهیه طرح اصلاح و اعتبارسنجی روی نسخه جدا قابل تصمیم‌گیری‌اند. در صورت تأیید بازیابی، پشتیبان را در مقصد جدا بازگردانید و مقادیر مالی، حساب‌ها، هویت اشتراک‌ها، قیود و وضعیت pending/attention را تطبیق دهید.
- نسخه قبلی برنامه را فقط با schema سازگار شروع کنید. اثرهای پنل بعد از snapshot و ابطال نشست‌ها را پیش از بازگشایی نوشتن تعیین تکلیف کنید. اگر مقصد بازیابی شد، فرمان آماده‌سازی را ابتدا روی نسخهٔ آزمایشی تمرین کنید.
- اگر failure فقط پس از رسیدن schema به head و هنگام ساخت ادمین رخ داده و ساختار و داده‌ها کامل بودن مهاجرت را تأیید می‌کنند، پس از اصلاح تنظیمات یا مجوز، اجرای دوبارهٔ فرمان مسیر قابل بررسی است. ادمین قدیمی دارای رمز پیش‌فرض باید از طریق ابزار مستند ریست رمز اصلاح شود.
